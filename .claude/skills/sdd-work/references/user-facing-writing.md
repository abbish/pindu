# 面向用户的内容怎么写

写作前先确定文档的主要读者与要帮助他完成的任务。面向拼读产品用户发布或展示的内容，从学习者的角度写：能获得什么、怎么使用、需要做什么。内部产品与工程资料按各自读者的任务组织，不能因为同在仓库里就混进用户文档。

## 1. 适用范围

| 内容 | 位置 | 细则 |
|---|---|---|
| 界面文案、提示与报错 | 前端页面、`AppError` 给用户的信息 | 另见 `deliver-frontend-react/references/ui-interaction-patterns.md` §6–7 |
| 更新说明 | `docs/releases/UNRELEASED.md`、`docs/releases/vX.Y.Z.md`（同时显示在 Release 页面和应用的「更新内容」弹窗里） | 本文 |
| 用户文档 | `README.md` / `README.en.md` 全文、`INSTALL.md`、`SECURITY.md` | 本文；操作和隐私所需的信息见第 4 节 |

不受本文约束：开发者及内部产品文档（`CLAUDE.md`、`CONTRIBUTING.md`、`docs/RELEASING.md`、`docs/agent-harness/`、`docs/product/`、`docs/promo/` 等）、提交信息、日志。

### 文档受众与入口

| 主要读者 | 文档与入口 | 帮助读者完成的任务 |
|---|---|---|
| 产品用户：英语学习者 | `README.md`、`README.en.md`、`INSTALL.md`、`SECURITY.md`、`docs/releases/` 中的更新说明 | 了解产品价值与功能，安装、使用、更新、处理问题，理解隐私与许可 |
| 开发者与维护者 | `CONTRIBUTING.md`、`docs/RELEASING.md`、工程设计与约定 | 开发、验证、维护与发布产品 |
| 产品策划与宣传制作人员 | `docs/product/`、`docs/promo/`、`docs/videos/`、`docs/posters/` 中的分析、方案与管理文档 | 定义定位与需求，验证假设，策划、制作和审核宣传素材 |
| 编码助手 | `CLAUDE.md`、`.claude/skills/`、工作记录 | 按约束执行任务，选择流程，恢复工作状态 |

受众由实际用途决定，不只看文件名或目录名：发布流程面向维护者，发布后的更新说明面向产品用户；海报设计说明面向制作人员，导出的海报面向目标观众。

每份文档确定一类主要读者。需要服务职责和任务明显不同的读者时，拆成不同文档，用各自入口访问，不能靠增加章节把受众混在同一篇里。正文、导航、相关链接与附录均遵循这个边界。

用户文档只放产品用途、使用方法、安装配置、帮助反馈、隐私与许可信息。开发命令、技术栈、架构与工程约定、产品定位方法与验证方案、宣传素材制作和管理归对应内部文档；不在用户文档中设开发章节或内部资料索引，也不以链接重新引入。开发资料从 `CONTRIBUTING.md` 进入，产品定位分析留在 `docs/product/`，宣传制作资料从 `docs/promo/README.md` 进入。

内部文档可以为核对事实或完成当前任务引用用户说明；跨受众引用要说明用途，引用不能成为复制另一类文档内容的理由。内部定位与制作说明可保留依据和过程，对外介绍、海报和视频只交付目标读者需要的结果。用户操作与隐私披露所需的技术信息按第 4 节处理。

## 2. 不写什么

| 不写 | 例子 |
|---|---|
| 文件、目录、路径 | `backups/`、`vocabulary.db`、数据目录、缓存目录 |
| 数据库与升级机制 | 数据库升级、迁移、表、索引、重建 |
| 安全与更新机制 | 签名、验签、公钥、`latest.json`、协议、端点 |
| 组件、依赖、版本 | ffmpeg、WordNet、pi、sidecar、Tauri、依赖升级、工具链 |
| 内部流程与术语 | 后台任务队列、job、IPC、缓存键、校验退回、模型名 |
| 测试与工程过程 | 「CI 构建通过」「已完成回归」「单元测试」 |
| AI 在做什么 | 「AI 正在整理字幕」「AI 没有交回结果」「模型没有提交…」「AI 认为…」：AI 是后台用的技术，进度、状态、结果、报错只说在做什么（「正在整理字幕」「字幕没有整理好，请再试一次」）；AI 老师里用老师的口吻（「老师没有答上来」） |
| 与用户无关的修复 | 重构、代码清理、构建脚本、开发工具 |

## 3. 换成用户的说法

| 技术写法 | 用户写法 |
|---|---|
| 首次启动会升级数据库，升级前自动备份到 `backups/` | 更新后第一次打开会稍等片刻，你的词汇本和学习记录都会保留 |
| 更新包签名校验失败 | 更新没有安装，为了安全请稍后重试或到官网下载 |
| ffmpeg 随应用分发，无需单独安装 | 视频功能装好即可使用，不需要另外安装软件 |
| 内置 WordNet 词典，识别不规则变形 | 能认出 went、bought、children 这类不规则变化 |
| 内容规划改为后台任务 | 生成短文时可以离开页面，回来接着看进度 |
| Windows 仅构建通过，未实际运行验证 | Windows 版本这次测试得较少，遇到问题欢迎反馈 |

写法要点：
- 写结果和用法，不写原因和机制：「现在可以……」「不再……」「……时会……」。
- 用应用里的名称称呼功能（词汇本、短文库、AI 老师、「设置 → 语音合成」），和界面保持一致。
- 功能名、按钮和开关可以带「AI」（「AI 老师」「AI 生成短文」「AI 选词」）；「设置」里配置 AI 模型、填 API Key 的地方，以及需要用户去那里处理的报错，可以说「AI 模型」「AI 服务」。除此之外不让 AI 当句子的主语。
- 一条只讲一件事，短句；修复写成「现在正常了的样子」，不写出错的技术原因。
- 只有用户能感知到的改动才写进更新说明。

## 4. 唯一的例外：用户必须亲自操作

只有用户必须亲自动手、并且不知道就做不下去时，才给出具体的技术信息，例如手动恢复备份、首次打开时在系统设置里放行、填写 API Key。`SECURITY.md` 的隐私披露（数据存在哪、发给谁）要求准确，也属于这一类。这时：
- 只写在用户文档里对应操作的步骤中，不写进更新说明和界面常驻文案。
- 用操作的语言写（「打开……，点……，把……复制回来」），先说为什么要做，再给步骤和路径。

## 5. 自查

写完后逐句问：一个不懂电脑的学习者读这句，是否知道「对我有什么变化 / 我要做什么」？不能回答的句子，删掉或改写。

再核对整篇的目录、导航、相关链接与附录：是否混入内部产品分析、开发与制作流程的入口？操作路径、服务配置与隐私披露按第 4 节判断，不能用例外容纳与使用无关的实现说明。

最后确认主要读者和目标任务是否一致：每个章节与链接都能帮助这类读者完成任务；制作说明与对外成品分别审查，内部过程不随成品发布。
