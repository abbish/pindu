# 面向用户的内容怎么写

拼读的用户是学英语的普通人（学生、家长、成人学习者），不是计算机从业者。凡是用户会看到的内容，都从用户的角度写：他能感知到什么变化、需要做什么。实现方式、存储位置、技术名词，用户不关心，也看不懂，一律不写。

## 1. 适用范围

| 内容 | 位置 | 细则 |
|---|---|---|
| 界面文案、提示与报错 | 前端页面、`AppError` 给用户的信息 | 另见 `deliver-frontend-react/references/ui-interaction-patterns.md` §6–7 |
| 更新说明 | `docs/releases/UNRELEASED.md`、`docs/releases/vX.Y.Z.md`（同时显示在 Release 页面和应用的「更新内容」弹窗里） | 本文 |
| 用户文档 | `README.md` / `README.en.md` 的功能、安装、隐私部分，`INSTALL.md` | 本文 |

不受本文约束：开发者文档（`CLAUDE.md`、`CONTRIBUTING.md`、`docs/RELEASING.md`、`docs/agent-harness/`、README 的「开发」一节）、提交信息、日志。

## 2. 不写什么

| 不写 | 例子 |
|---|---|
| 文件、目录、路径 | `backups/`、`vocabulary.db`、数据目录、缓存目录 |
| 数据库与升级机制 | 数据库升级、迁移、表、索引、重建 |
| 安全与更新机制 | 签名、验签、公钥、`latest.json`、协议、端点 |
| 组件、依赖、版本 | ffmpeg、WordNet、pi、sidecar、Tauri、依赖升级、工具链 |
| 内部流程与术语 | 后台任务队列、job、IPC、缓存键、校验退回、模型名 |
| 测试与工程过程 | 「CI 构建通过」「已完成回归」「单元测试」 |
| 与用户无关的修复 | 重构、代码清理、构建脚本、开发工具 |

## 3. 换成用户的说法

| 技术写法 | 用户写法 |
|---|---|
| 首次启动会升级数据库，升级前自动备份到 `backups/` | 更新后第一次打开会稍等片刻，你的词汇本和学习记录都会保留 |
| 更新包签名校验失败 | 更新没有安装，为了安全请稍后重试或到官网下载 |
| ffmpeg 随应用分发，无需单独安装 | 视频功能装好即可使用，不需要另外安装软件 |
| 内置 WordNet 词典，识别不规则变形 | 能认出 went、bought、children 这类不规则变化 |
| 内容规划改为后台任务 | 生成短文时可以离开页面，回来接着看进度 |
| Windows / Linux 仅构建通过，未实际运行验证 | Windows 和 Linux 版本这次测试得较少，遇到问题欢迎反馈 |

写法要点：
- 写结果和用法，不写原因和机制：「现在可以……」「不再……」「……时会……」。
- 用应用里的名称称呼功能（词汇本、短文库、AI 老师、「设置 → 语音合成」），和界面保持一致。
- 一条只讲一件事，短句；修复写成「现在正常了的样子」，不写出错的技术原因。
- 只有用户能感知到的改动才写进更新说明。

## 4. 唯一的例外：用户必须亲自操作

只有用户必须亲自动手、并且不知道就做不下去时，才给出具体的技术信息，例如手动恢复备份、首次打开时在系统设置里放行、填写 API Key。`SECURITY.md` 的隐私披露（数据存在哪、发给谁）要求准确，也属于这一类。这时：
- 只写在用户文档里对应操作的步骤中，不写进更新说明和界面常驻文案。
- 用操作的语言写（「打开……，点……，把……复制回来」），先说为什么要做，再给步骤和路径。

## 5. 自查

写完后逐句问：一个不懂电脑的学习者读这句，是否知道「对我有什么变化 / 我要做什么」？不能回答的句子，删掉或改写。
