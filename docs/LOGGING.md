# 日志规范

本文是拼读日志的完整规范，CLAUDE.md §7.3 有摘要。
**新增或修改功能时，一律按本文判断要不要记日志、记在哪一级。** 日志只写本机文件，不上报，没有任何远程埋点。

## 1. 目的：出了问题能查清

我们记日志，是为了用户反馈“没反应 / 结果不对 / 报错了”时，单看日志就能回答三件事：

1. **发生了什么**：用户做了什么操作，后端做了哪些改数据的动作，结果如何。
2. **哪里失败了**：失败的位置，以及原始原因（不是给用户看的那句提示）。
3. **为什么是这个结果**：自动发生的事情（自动开始 / 完成、复习调度、AI 重试与校验退回、后台任务），以及当时的关键数字。

做不到这三点的日志是噪音。内容只有“进入了某个函数”的那种也算噪音。

## 2. 级别：一条日志该记几级

| 级别 | 什么时候用 | 例子 |
|---|---|---|
| **ERROR** | 操作失败，需要有人排查 | 命令失败（`API … FAILED`）、AI 模型报错或进程失败、后台任务失败、界面崩溃、启动或升级失败 |
| **WARN** | 没失败，但走了降级或自动恢复，或者结果可疑 | AI 自动重试、结果没过校验被退回、没交出结果、读设置失败改用默认值、统计没更新上、找不到可选组件 |
| **INFO** | 用户动作与业务结果（改数据的命令一条一行） | 改数据的命令、练习完成摘要、计划状态变化、后台任务提交 / 结束、AI 运行开始 / 完成、清空数据、启动 |
| **DEBUG** | 排查明细，平时不需要 | 只读查询（`get_` / `list_` / `preview_` / `find_` / `diagnose_`）、SQL、发给模型的消息、工具返回的结果 |

用户可以在「设置 → 通用 → 诊断」选择最低级别。选 WARN 时 INFO 和 DEBUG 都不写，所以**排查问题必需的信息不能只放在 DEBUG**。

判断方法：
- 会被频繁、反复调用（页面加载、轮询、每个单词、每一步）→ 不能是 INFO，降为 DEBUG，或者汇总成一条（像练习完成摘要那样）。
- 错误被 `.ok()` / `let _ =` / `unwrap_or` 吞掉，又影响结果 → 至少记一条 WARN，写清降级成了什么。
- 用户输入不合法这类校验失败，经 `api_response` 记 ERROR 即可，不用重复记。

## 3. 记在哪里

| 场景 | 位置 | 做法 |
|---|---|---|
| 每个 Tauri 命令 | handler | 入口 `logger.api_request(cmd, 参数摘要)`，出口 `logger.api_response(cmd, ok, 结果摘要)`；级别由命令名自动判断 |
| AI 任务 | `agent/run_log.rs`（`run_task_cancellable` 已统一接入） | 新任务走 `run_task` / `run_task_cancellable` 就会自动记录，不要另写开始 / 结束日志；任务自己的业务摘要（如“请求 20 词，成功 19”）记一条 INFO |
| 后台任务 | `lib.rs::log_job`（Jobs 的 emit 钩子） | 用 `Jobs::spawn` 提交就会自动记录提交 / 完成 / 取消 / 失败 |
| 自动发生的业务变化 | 发生的那个函数（如 `transition_conn`、`srs::sync_today`） | 记 INFO，写清前后状态和原因；如果在事务里，注明“随本次操作一起保存” |
| 降级 / 吞错 | 吞错的地方 | WARN，写清降级成了什么 |
| 前端 | `apiClient.log(level, component, message, details)` → `write_client_log` | 只用于后端看不到的错误：界面崩溃、未捕获异常（已在 `main.tsx` / `ErrorBoundary` 接入），以及没进到命令里的 IPC 错误（`client.ts` 已接入）。不要用它记普通操作，这些操作后端已经记过了 |

## 4. 一条日志怎么写

- **组件名**：大写英文单词，按功能域取，如 `API` `AGENT` `JOB` `STUDY_PLAN` `SRS` `TTS` `VIDEO` `DATABASE` `STARTUP`。前端的自动带 `UI:` 前缀。不要用 `*_DEBUG` 这类临时名字。
- **message**：一句话写清“谁 + 发生了什么 + 结果”，带上能定位的 ID（计划 / 日程 / 会话 / 任务 ID、AI 运行编号）。中文英文都可以，同一组件内保持一致。
- **details**：放原始错误、stderr、参数摘要这类较长的内容；单条超过 4000 字会被截断。
- **同一件事的多行要能串起来**：AI 运行用 `[任务名#编号]`，后台任务用 `[job-N]` 开头。
- **数字带单位**：`用时 3.2s`、`有效时长 120s`、`正确率 85.0%`（先确认字段已经是百分数还是 0–1 的小数）。

## 5. 不能记的内容

- **密钥**：API Key、Access Token。AI 相关的日志统一经 `RunLog` 去掉密钥；其他地方记参数时只写 `api_key_changed: true` 这类标记。
- **大段用户内容**：导入的原文、整段短文、讲解全文，只记长度（`text chars: 1234`）。AI 消息与模型输出只在 DEBUG 记，并会截断。
- **每次都会触发的明细**放 INFO：每个单词的作答、每个进度更新、轮询结果。要么降到 DEBUG，要么汇总成一条。

## 6. 存储

`<数据目录>/logs/app.log`，每行一条 JSON。超过 5MB 轮转为 `app.1.log` … `app.4.log`，总量上限约 25MB。写入由后台线程完成；读取只读文件末尾。不需要另建日志文件。

## 7. 改动前后自查

新增功能或修改流程时，对照下面几条检查：

- [ ] 新命令有 `api_request` / `api_response`，参数摘要里没有密钥和大段文本。
- [ ] 失败路径能在日志里看到原始原因，没有被转成用户提示之后就丢了。
- [ ] 自动发生的变化（状态、调度、清理、重试）有 INFO 或 WARN。
- [ ] 吞掉的错误如果影响结果，有 WARN。
- [ ] 没有把高频明细记成 INFO；切到 WARN 级别时，仍能看出问题。
- [ ] AI 任务走 `run_task*`，后台任务走 `Jobs::spawn`，没有另写一套开始 / 结束日志。
