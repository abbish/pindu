## D01 · 2026-10-06 · 引入现成 agent harness，而非继续自研 LLM 调用层

- **背景**：现有 `ai_service` 直连 async-openai，参数处理分散（曾出现温度写死导致 Kimi K3 报错）、无法传思考档等扩展参数；未来要做场景对话、练习助手等多轮交互。
- **决定**：引入可内置执行的 agent harness（不是 LangChain 类 framework），由它负责模型适配、工具循环、流式、会话。
- **决定人**：用户（明确要求“harness 选择要更完备”）。

## D02 · 2026-10-06 · 选型 pi，RPC 模式作为 Tauri sidecar

- **候选**：pi（TS）、opencode（TS，服务端模式）、Goose（Rust）、DeepSeek Harness（v0.1 预览）、Codex。
- **决定**：pi（`@earendil-works/pi-coding-agent`），RPC 模式（stdin/stdout JSONL）。
- **理由**（spike 实测）：核心最轻、专为嵌入设计 RPC；工具白名单 + 自定义工具；内置 Moonshot / DeepSeek / MiniMax / OpenRouter 目录与思考档映射；场景对话的流式、工具、上下文、重启恢复会话全部通过。
- **备选**：Goose（纯 Rust 进程内）；在 pi 出现阻断问题时再评估。

## D03 · 2026-10-06 · sidecar 形态：bun 编译自建 host 为单文件，工具编译进二进制

- **背景**：直接编译 pi 自带入口后无法在运行时加载 `.ts` 扩展（缺 jiti）；用系统 Node 运行则需捆绑 Node（116MB）+ node_modules（159MB）。
- **决定**：自建 `agent/src/host.ts` 调用 `main(["--mode","rpc", …], { extensionFactories })`，`bun build --compile` 成单文件（实测约 70MB / 平台）。
- **影响**：每平台安装包增加约 70MB——**用户已确认可接受**（2026-10-06）。工具改动需重新编译 sidecar。

## D04 · 2026-10-06 · 模型配置统一：RedLark 表为真源，按 pi 模型概念扩字段，sidecar 内转换为 models.json

- **背景**：用户提出“模型配置统一到适配 pi 封装好的模型配置数据结构上”。
- **决定**：
  1. 数据库仍是唯一真源（设置页、密钥、默认模型）；不直接让用户编辑 pi 的 models.json。
  2. 提供商增加 `pi_provider`（映射到 pi 内置 provider，复用其接口类型、兼容参数、模型目录）与 `api`（自定义 provider 的接口类型）；模型增加 `thinking_level`、`extra_params`（→ `samplingParams`）、`context_window`、`reasoning`。
  3. 转换在 sidecar 内完成：内置目录中已有的模型写 `modelOverrides`，没有的写 `models` 追加；自定义 provider 写完整定义。
  4. 密钥只经 `REDLARK_KEY_<provider_id>` 环境变量注入，models.json 中以 `$REDLARK_KEY_<id>` 引用。
- **理由**：已实测 pi models.json 支持对内置 provider 追加模型、覆盖参数、自定义 provider 用环境变量取 Key；只有 sidecar 能读到 pi 的内置目录，Rust 不需要复制这份知识。

## D05 · 2026-10-06 · 结构化结果通过 `submit_*` 工具交付，确定性工作放进工具

- **依据**：spike 中模型自行计数词频准确率 0.92–0.99，交给 `tokenize_text` 工具后为 1.0；工具参数天然是结构化 JSON，免去 CSV/JSON 文本解析。
- **决定**：所有一次性任务以 `submit_*`（`terminate: true`）交付；分词计数、格式校验、日期排期等由工具完成。

## D06 · 2026-10-06 · 进程模型：每个 agent 会话一个 sidecar 进程

- **决定**：一次性任务每次启动一个进程、完成即退出（启动 0.5–1.7s，相对 LLM 耗时可忽略）；对话会话在会话期间保持进程，会话文件持久化到 `<app_data>/agent/sessions`，重开时 `--session` 恢复。
- **理由**：实现最简单、隔离最好（崩溃不影响其它任务）；需要时再引入进程池。

## D07 · 2026-10-06 · 迁移策略：逐任务替换，保留旧实现开关，最后删除

- **决定**：按 提词 → 拼读分析 → 学习计划 → 场景对话 的顺序迁移；每步保留旧实现作为回退，稳定后统一删除 async-openai 路径与轮询进度管理器。
- **工作方式**：当前工作区的未提交改动暂不提交（用户未要求提交）；harness 改动在同一工作区按批次推进，并在 `.claude/work/agent-harness-integration/` 持续记录。

## D08 · 2026-10-06 · 提词结果在 Rust 侧做确定性校正；sidecar 启动失败才回退旧实现

> 第 2 点（回退旧实现、`REDLARK_LEGACY_AI`）已被 **D12** 取代：旧实现已删除，不再回退。

- **决定**：
  1. `submit_words` 的结果在 Rust 中再处理：只保留原文中真实出现的词（防编造），频率一律以 Rust 的确定性分词为准，重点模式再次过滤功能词。sidecar 的 `tokenize_text` 与 Rust `tokenize_words` 同规则，各有测试。
  2. 回退策略：只有「sidecar 无法启动」（错误前缀 `SPAWN_FAILURE`）时回退旧的 async-openai 实现并记错误日志；模型报错、超时等不回退（避免掩盖问题、重复计费）。`REDLARK_LEGACY_AI=1` 可强制旧实现。
- **影响**：提词结果频率准确率不依赖模型；旧实现在全部任务迁移完成前保留。

## D09 · 2026-10-06 · 每个 sidecar 进程独立 agentDir；持久会话推迟到 H5

- **背景**：models.json 写在 agentDir；多个任务并发时共享目录会互相覆盖。
- **决定**：每次运行在 `<app_data>/agent/runs/<任务>-<uuid>/` 下建独立 agentDir（含 config.json、system.md、models.json），进程结束删除；工作目录统一为空目录 `<app_data>/agent/cwd`。`SessionMode` 目前只有一次性模式，持久会话（`--session-dir` / `--session`）在 H5 场景对话时加入（spike 已验证可行）。

## D10 · 2026-10-07 · 设置页按 pi 模型体系配置；生成参数整体替换；pi 目录由 sidecar 导出

- **决定**：
  1. 提供商可「映射到 pi 内置提供商」（下拉来自 pi 目录）；不映射时为自定义端点，需选接口类型（openai-completions / openai-responses / anthropic-messages）。
  2. 模型的六项生成参数（最大输出、温度、思考档、额外参数、上下文窗口、推理）作为 `ModelGenerationSettings` 整体保存（`generation` 给出时全部替换，空 = 不发送），取代前一天加入的 `clear_max_tokens / clear_temperature` 标志。
  3. pi 内置目录由 `redlark-agent --redlark-catalog` 导出（不联网、不启动 agent），Rust 进程内缓存；「同步模型」对已映射的提供商以目录为主、合并远端 `/models`，远端失败时只用目录。
  4. 思考档选项按目录中该模型支持的档位过滤（如 Kimi K3 只有 low / high / max）。
- **依据**：实测额外参数经 samplingParams 原样到达模型（K3 对 `top_p=0.1` 返回 “only 0.95 is allowed”）；目录 41 个提供商、1537 个模型。
- **注意**：Kimi K3 固定 `temperature=1`、`top_p=0.95`，其它值会被拒绝。

## D11 · 2026-10-07 · 拼读分析：submit_phonics 自带校验并让模型重交；缺失单词显式失败

- **决定**：
  1. 批量拼读分析改为 agent 任务 `phonics-batch`：提示词沿用原规则知识库（`prompts/agent/phonics_batch.md`），输出改为调用 `submit_phonics`。
  2. `submit_phonics` 在 sidecar 内做确定性校验——音节去掉连字符必须拼回单词、IPA 用斜杠包围、拼读规则必须原样取自规则表（新增 `Irregular | 不规则拼读` 兜底）、必填字段非空；不通过则作为工具错误返回问题清单，模型修正后重交，通过才结束本轮。
  3. Rust 只接受本批请求中的单词（忽略大小写、去重）；模型没有返回的单词标记为失败（旧实现会让它们一直停留在“分析中”）。
  4. 两条批量管线（`analyze_extracted_words`、`analyze_text_with_batching`）统一经 `services/phonics_analysis.rs::PhonicsBatchAnalyzer`，回退策略同 D08。
- **未迁移**：单词级 `analyze_phonics_with_model`（JSON 版）仍走旧实现，随 H4 一并评估。

## D12 · 2026-10-07 · 全部 LLM 功能迁移到 agent；无界面入口的旧路径直接删除；迁移完成后移除回退

- **背景**：用户要求“全部迁移到 agent”，并按场景优化提示词。
- **决定**：
  1. 盘点前端实际调用：单词级拼读分析（`analyze_phonics_with_model`，仅被未渲染的 `WordImporter` 组件使用）与 `analyze_text_with_batching` 没有界面入口——**直接删除**（含 `phonics_agent.md`、JSON 拼读解析、`AIService::chat_completion`），不做迁移。
  2. 「测试模型」改为 agent 无工具任务（`-nt`），走与业务一致的调用链（思考档、额外参数都生效）。
  3. 新增通用 `agent::tasks::run_task`（启动 → 一轮对话 → 用量 → 清理），各任务只负责提示词、工具与结果校正。

## D13 · 2026-10-07 · 学习计划：模型只做“排序 + 难度 / 优先级判断”，日程由代码确定性计算

- **背景**（需求调研）：旧实现让模型输出整份日程 JSON（日期、每天哪些词、复习第几次），无任何语义校验——会漏词（漏掉的词静默退出计划）、日期越界、同一天同词既新学又复习（该天永远无法“完成”）、长词表输出被截断；提示词的复习规则互相矛盾（7 天表只有 3 次复习但复习次数可选 4–5、“均分”与“前 30% 学 60%”冲突），语气面向成人。
- **决定**：
  1. 模型任务 `plan-word-order`：读入全部单词（id / 单词 / 中文），给出**学习顺序**（由易到难、同主题或同拼读模式相邻）以及每词 `difficulty`（1–5，按小学生视角的拼读难度）与 `priority`（high / medium / low），通过 `submit_learning_order` 交付。
  2. Rust 确定性生成日程（`services/study_planning.rs`）：
     - 学习天数 L = ⌈周期 × 比例⌉（轻松 100% / 标准 80% / 强化 60%），并保证每天新词不超过上限（15 / 30 / 50），必要时把 L 延长到整个周期；
     - 按模型顺序把新词均分到前 L 天（余数给前几天）；
     - 复习按间隔重复 +1、+2、+4、+7、+15 天取前 N 次（N = 复习次数），超出周期的复习丢弃；同词同日不会重复；
     - 元数据（总词数、起止日期、计划类型）全部由代码计算；空白日不生成。
  3. 模型漏掉的词追加到顺序末尾（难度按长度估计、优先级 medium），重复 / 未知 id 忽略——保证每个词恰好新学一次。
  4. 输出仍为原 `StudyPlanAIResult` 结构，预览、保存、详情页、日历、练习均不需改动；规划进度仍写原进度管理器（前端轮询契约不变），取消通过 RPC `abort` 中止 sidecar。

## D14 · 2026-10-07 · 单词例句随拼读分析一并生成；TTS 用固定语音指令稳定朗读风格

- **背景**：用户希望创建单词本时为单词生成例句，练习时既能听单词也能听例句；并反馈“单词朗读每次风格有些不同”。
- **调查**：后端 TTS 缓存有效（键 = 文本 + 音色 + 资源 + 语速 + 采样率，测试库中 `Cat` 命中 5 次，同一文本之后永远是同一段音频）；差异来自豆包 2.0 是生成式模型——同一文本连续合成 3 次结果都不同（实测时长 1.06–1.63s），每个新词第一次合成时语调随机，单个单词尤其容易读成疑问 / 夸张语气。
- **决定**：
  1. 例句在 `phonics-batch` 同一次调用里生成（不另起任务）：`submit_phonics` 增加 `example_sentence` / `example_translation`，工具校验 3–12 词、句首大写句末标点、纯英文、包含该单词（允许复数 / -ing / -ed 等常见变形）、翻译含中文；提示词规定小学课本难度、贴近孩子生活、不套模板。
  2. 存储：迁移 040 给 `words` 加两列（可空）；例句与翻译成对保存，缺一项都不存；再次导入时新结果没有例句则保留原例句。已有单词不回填。
  3. 练习页：第一步显示完整例句（高亮单词）、第二步挖空、第三步只显示中文，作答后显示完整例句；例句可点按朗读，自动朗读只读单词，读完后预取例句音频。
  4. TTS 增加 `style`（word / sentence）：对支持指令的 2.0 资源（seed-tts-2.0 / seed-icl-2.0）通过 `additions.context_texts` 发送固定的“老师示范”指令，风格（带版本号）进入缓存键；1.0 音色不发指令。旧缓存因此对单词失效一次（重新合成后固定）。
- **未定**：指令能多大程度减少差异需要人耳判断；A/B 样本已交给用户试听，不满意可去掉指令或改用 1.0 音色。

## D15 · 2026-10-07 · 每词 5–8 条例句（一对多表），练习页左右两栏

- **背景**：用户要求练习页改为左右两栏、右栏列出例句并可点选朗读，每个单词至少 5 条例句；同时页面要按窗口高度自适应，避免输入框 / 确认按钮被挤出视口。
- **决定**：
  1. 新表 `word_examples`（迁移 041，`ON DELETE CASCADE`，`sort_order` 保序），040 的单列例句迁入后不再读写——不在 `words` 上堆 example_2…example_8 列。
  2. `submit_phonics` 的 `examples` 改为 5–8 条 `{sentence, translation}`，逐条沿用 D14 的校验并拒绝重复句；提示词要求由易到难（第 1 条最简单，用于自动朗读）、场景与句式各不相同。
  3. Rust 侧只保存句子与翻译齐全的例句、去重；重新导入时新结果有例句才整体替换。
  4. 练习页：页面固定为窗口高度，左栏卡片信息区内部滚动、输入区固定在底部；右栏例句列表自身滚动；≤900px 宽改为上下排列并恢复页面滚动。例句显示随步骤变化（完整 / 挖空 / 仅中文，作答后完整）。自动朗读 = 单词 + 第 1 条例句；点击任一例句朗读该句，只预取第 1 条。
- **代价**（15 词评测）：拼读批量分析耗时 49s → 142s、费用 $0.031 → $0.085；校验退回 2 次。可选优化：例句拆成与拼读并行的独立任务，或提高批次并发。

## D16 · 2026-10-07 · 单词讲解：agent 实时生成 Markdown，流式显示，按单词缓存

- **背景**：学生不理解某个单词时，希望在练习页右栏看到像老师一样的深入讲解（结合例句与单词基础知识），可缓存、可刷新。
- **决定**：
  1. 新任务 `word-explain`（`prompts/agent/word_explain.md`，无工具）：输入单词已有资料（释义、词性、音标、音节、拼读规则与讲解、全部例句），输出固定八节的 Markdown（一句话记住 / 怎么读怎么拼 / 意思和用法 / 变一变 / 例句里的它 / 别和它搞混 / 记忆小妙招 / 考考你）。这是展示用的长文本，**例外于 D05“结构化结果只经 submit_* 工具”**：直接取 assistant 文本，Rust 侧只做去包裹代码块与最短长度校验。
  2. 流式：`run_task` 的 `TextDelta` 经 Tauri 事件 `word-explanation-delta {requestId, wordId, delta}` 推给前端，前端按 requestId 丢弃过期增量；完成后以服务端清洗后的全文替换。
  3. 缓存：`word_explanations`（迁移 042，一词一份，`ON DELETE CASCADE`）；打开页签先读缓存，没有才生成；“重新生成”覆盖缓存。换词后旧请求仍会写缓存（下次直接打开）。
  4. 练习页右栏改为「例句 / 单词讲解」页签（两个页签都保持挂载，切换不打断生成）；第二、三步作答前讲解默认遮住（讲解含单词拼写），可手动“仍然查看”，作答后自动显示。
  5. 前端用 `react-markdown` + `remark-gfm` 渲染（不渲染原始 HTML）。
- **实测**（K3 low，cake）：21.0s、978 字、518 段增量。

## D17 · 2026-10-07 · 讲解改用正规记忆方法与正确性自查；例句可由 AI 补充 / 重新生成

- **背景**：用户质疑讲解里的“记忆小妙招”（如把 all 说成 ball 拿掉 b、“大家都能玩所以是全部”）不符合英语母语者的学习习惯，要求审视专业性与正确性；并希望例句页签也能让 AI 补充或重新生成，交互与讲解一致。
- **基线评测**（`agent/eval/eval-explain.mjs`，8 类单词）：发现字母赋义（“c 像盘子、k 是刀”“i 是蜡烛、gh 是幽灵”）、错误构词（teacher = tea + cher“喝茶的人”）、谐音（elephant）、读音说法不准（said “ai 读短音”）。
- **决定**：
  1. `word_explain.md` 改为以成熟方法为骨架：音—字母对应（orthographic mapping）、词族 / 押韵（onset-rime）、构词（morphology）、音节分块、心形词（Heart Words，只用于真正不规则的部分）、看-说-盖-写-查（Look-Say-Cover-Write-Check）、边拼边说、画面 + 句子；明确禁止中文谐音、编造词源、无关词语义硬联系、给字母赋予含义。
  2. 增加“输出前逐条自查”：词族成员必须同拼同音（eight ∉ -ight）、心形部分不含 igh/ai/ph 等规律组合、同音词必须完全同音、对其他词读音的断言必须准确、构词必须真实。

## D26 · 2026-10-07 · 短文：不限制词数，内容质量优先

- **背景**：用户指出“合计最多 15 个词”没有道理；按“每 N 个词放一个目标词”的密度规则会让短文模式化，成为“按规则对齐的语法句子”，失去阅读价值。实测（16 个必用词，A1）也印证：模型写成按行程逐词打卡的流水账，并出现为用词而硬凑的句子。
- **决定**：
  1. 不设目标词上限（至少 1 个）；篇幅只作为长度与丰富程度的参考，为自然用上所有必用词可以适当写长；工具只拦明显没写完整的短文（< 参考下限的 60%），不再按词数区间退回重写；AI 挑词“最多 N 个、宁缺毋滥”。
  2. 提示词改为“先当作家再当老师”：围绕一个核心事件展开、不写流水账、具体细节与对话、句式多样、目标词为内容服务，交稿前自查“去掉目标词故事还值得读吗”。
  3. `submit_passage` 增加必填的 `outline`（goal / problem / turn / ending），先构思再写；写短文任务思考档改为 medium。
- **实测**（Kimi K3，A1）：5 个必用词 + 挑 3 个 → 有起因、连续小麻烦、解决与幽默收尾的故事（99 词，35s）；16 个必用词 → 后半段有完整情节（130 词，52s），前半段受词表本身（整套出行流程）影响仍偏行程顺序。代价：生成时间约增加 10–25 秒。

- **背景**：用户提出不必一次只生成一篇：先让 AI 根据选定的词给出内容规划，由用户决定怎么生成；规划必须由 AI 生成与提议。

  1. 新 agent 任务 passage-plan（`passage_plan.md`，工具 `submit_passage_plan`，medium 思考档）：决定写 1–4 篇，每篇给英文标题、中文构思（主角与目标 / 麻烦或意外 / 发展与解决 / 结尾）、所用的词、建议篇幅，并用 `note` 说明为什么这样规划；只在词能自然放进同一个好故事时写一篇，词分属不同场景或一篇装不下时拆分。用户可写调整意见重新规划。
  2. Rust `plan_from_submission` 校验：词只来自必用词与候选池（AI 挑选合计 ≤ ai_pick）、每词只归一篇、漏掉的必用词补进词最少的一篇、无词或无构思的篇目丢弃。规划不入库。
  3. 生成时 `GeneratePassageRequest.plan_item` 带上用户确认（可改标题、构思、篇幅、取消某篇）的那一篇，写作消息加入“按已确认的构思来写”，词以数据库为准（有 id 的词必须存在）。前端逐篇顺序生成，显示每篇状态，失败可单独重试。
- **实测**（Kimi K3）：16 个出行词 → 拆成“机场 + 海关”“酒店 + 城市”两篇，各有核心事件（31s）；5 个词 → 一篇完整故事，未挑无关候选词（15s）；按构思写的短文严格遵循人物、事件与结尾并补充了细节（45s）。

## D33 · 2026-10-08 · 新建短文：AI 按条件挑词

- **背景**：单词本词多时，逐个勾选必用词很费事；原来的「让 AI 再挑几个」藏在表格下面，最多 12 个，只从来源前 120 个词里按场景挑，不看学习情况。

## D35 · 2026-10-08 · AI 任务统一的等待上限，可在设置里调

- **背景**：各 agent 任务原来各自写死超时（120–600 秒）。长视频规划、慢模型的深度思考会超过，用户只看到「响应超时」，也没有办法调整。
- **决定**：删掉任务各自的超时；所有 agent 任务共用「设置 → AI 助手 → 每次最长等待」（`app_settings` 键 `agent.timeout_minutes`，3–60 分钟，默认 15），`agent_settings::task_timeout` 读取，启动时与保存设置后生效。超时的提示说明等了多久、去哪里调长。
- **原因**：上限只是防止卡死的兜底，不是性能指标；任务都能取消，后台任务也不挡界面，默认放宽不会伤害体验。
