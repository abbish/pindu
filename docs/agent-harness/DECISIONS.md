## D01 · 2026-10-06 · 引入现成 agent harness，而非继续自研 LLM 调用层

- **背景**：现有 `ai_service` 直连 async-openai，参数处理分散（曾出现温度写死导致 Kimi K3 报错）、无法传思考档等扩展参数；未来要做场景对话、练习助手等多轮交互。
- **决定**：引入可内置执行的 agent harness（不是 LangChain 类 framework），由它负责模型适配、工具循环、流式、会话。
- **决定人**：用户（明确要求“harness 选择要更完备”）。

## D02 · 2026-10-06 · 选型 pi，RPC 模式作为 Tauri sidecar

- **候选**：pi（TS）、opencode（TS，服务端模式）、Goose（Rust）、DeepSeek Harness（v0.1 预览）、Codex。
- **决定**：pi（`@earendil-works/pi-coding-agent`），RPC 模式（stdin/stdout JSONL）。
- **理由**（spike 实测）：核心最轻、专为嵌入设计 RPC；工具白名单 + 自定义工具；内置 Moonshot / DeepSeek / MiniMax / OpenRouter 目录与思考档映射；场景对话的流式、工具、上下文、重启恢复会话全部通过。
- **备选**：Goose（纯 Rust 进程内）；在 pi 出现阻断问题时再评估。

## D03 · 2026-10-06 · sidecar 形态：bun 编译自建 host 为单文件，工具编译进二进制

- **背景**：直接编译 pi 自带入口后无法在运行时加载 `.ts` 扩展（缺 jiti）；用系统 Node 运行则需捆绑 Node（116MB）+ node_modules（159MB）。
- **决定**：自建 `agent/src/host.ts` 调用 `main(["--mode","rpc", …], { extensionFactories })`，`bun build --compile` 成单文件（实测约 70MB / 平台）。
- **影响**：每平台安装包增加约 70MB——**用户已确认可接受**（2026-10-06）。工具改动需重新编译 sidecar。

## D04 · 2026-10-06 · 模型配置统一：RedLark 表为真源，按 pi 模型概念扩字段，sidecar 内转换为 models.json

- **背景**：用户提出“模型配置统一到适配 pi 封装好的模型配置数据结构上”。
- **决定**：
  1. 数据库仍是唯一真源（设置页、密钥、默认模型）；不直接让用户编辑 pi 的 models.json。
  2. 提供商增加 `pi_provider`（映射到 pi 内置 provider，复用其接口类型、兼容参数、模型目录）与 `api`（自定义 provider 的接口类型）；模型增加 `thinking_level`、`extra_params`（→ `samplingParams`）、`context_window`、`reasoning`。
  3. 转换在 sidecar 内完成：内置目录中已有的模型写 `modelOverrides`，没有的写 `models` 追加；自定义 provider 写完整定义。
  4. 密钥只经 `REDLARK_KEY_<provider_id>` 环境变量注入，models.json 中以 `$REDLARK_KEY_<id>` 引用。
- **理由**：已实测 pi models.json 支持对内置 provider 追加模型、覆盖参数、自定义 provider 用环境变量取 Key；只有 sidecar 能读到 pi 的内置目录，Rust 不需要复制这份知识。

## D05 · 2026-10-06 · 结构化结果通过 `submit_*` 工具交付，确定性工作放进工具

- **依据**：spike 中模型自行计数词频准确率 0.92–0.99，交给 `tokenize_text` 工具后为 1.0；工具参数天然是结构化 JSON，免去 CSV/JSON 文本解析。
- **决定**：所有一次性任务以 `submit_*`（`terminate: true`）交付；分词计数、格式校验、日期排期等由工具完成。

## D06 · 2026-10-06 · 进程模型：每个 agent 会话一个 sidecar 进程

- **决定**：一次性任务每次启动一个进程、完成即退出（启动 0.5–1.7s，相对 LLM 耗时可忽略）；对话会话在会话期间保持进程，会话文件持久化到 `<app_data>/agent/sessions`，重开时 `--session` 恢复。
- **理由**：实现最简单、隔离最好（崩溃不影响其它任务）；需要时再引入进程池。

## D07 · 2026-10-06 · 迁移策略：逐任务替换，保留旧实现开关，最后删除

- **决定**：按 提词 → 拼读分析 → 学习计划 → 场景对话 的顺序迁移；每步保留旧实现作为回退，稳定后统一删除 async-openai 路径与轮询进度管理器。
- **工作方式**：当前工作区的未提交改动暂不提交（用户未要求提交）；harness 改动在同一工作区按批次推进，并在 `.claude/work/agent-harness-integration/` 持续记录。

## D08 · 2026-10-06 · 提词结果在 Rust 侧做确定性校正；sidecar 启动失败才回退旧实现

> 第 2 点（回退旧实现、`REDLARK_LEGACY_AI`）已被 **D12** 取代：旧实现已删除，不再回退。

- **决定**：
  1. `submit_words` 的结果在 Rust 中再处理：只保留原文中真实出现的词（防编造），频率一律以 Rust 的确定性分词为准，重点模式再次过滤功能词。sidecar 的 `tokenize_text` 与 Rust `tokenize_words` 同规则，各有测试。
  2. 回退策略：只有「sidecar 无法启动」（错误前缀 `SPAWN_FAILURE`）时回退旧的 async-openai 实现并记错误日志；模型报错、超时等不回退（避免掩盖问题、重复计费）。`REDLARK_LEGACY_AI=1` 可强制旧实现。
- **影响**：提词结果频率准确率不依赖模型；旧实现在全部任务迁移完成前保留。

## D09 · 2026-10-06 · 每个 sidecar 进程独立 agentDir；持久会话推迟到 H5

- **背景**：models.json 写在 agentDir；多个任务并发时共享目录会互相覆盖。
- **决定**：每次运行在 `<app_data>/agent/runs/<任务>-<uuid>/` 下建独立 agentDir（含 config.json、system.md、models.json），进程结束删除；工作目录统一为空目录 `<app_data>/agent/cwd`。`SessionMode` 目前只有一次性模式，持久会话（`--session-dir` / `--session`）在 H5 场景对话时加入（spike 已验证可行）。

## D10 · 2026-10-07 · 设置页按 pi 模型体系配置；生成参数整体替换；pi 目录由 sidecar 导出

- **决定**：
  1. 提供商可「映射到 pi 内置提供商」（下拉来自 pi 目录）；不映射时为自定义端点，需选接口类型（openai-completions / openai-responses / anthropic-messages）。
  2. 模型的六项生成参数（最大输出、温度、思考档、额外参数、上下文窗口、推理）作为 `ModelGenerationSettings` 整体保存（`generation` 给出时全部替换，空 = 不发送），取代前一天加入的 `clear_max_tokens / clear_temperature` 标志。
  3. pi 内置目录由 `redlark-agent --redlark-catalog` 导出（不联网、不启动 agent），Rust 进程内缓存；「同步模型」对已映射的提供商以目录为主、合并远端 `/models`，远端失败时只用目录。
  4. 思考档选项按目录中该模型支持的档位过滤（如 Kimi K3 只有 low / high / max）。
- **依据**：实测额外参数经 samplingParams 原样到达模型（K3 对 `top_p=0.1` 返回 “only 0.95 is allowed”）；目录 41 个提供商、1537 个模型。
- **注意**：Kimi K3 固定 `temperature=1`、`top_p=0.95`，其它值会被拒绝。

## D11 · 2026-10-07 · 拼读分析：submit_phonics 自带校验并让模型重交；缺失单词显式失败

- **决定**：
  1. 批量拼读分析改为 agent 任务 `phonics-batch`：提示词沿用原规则知识库（`prompts/agent/phonics_batch.md`），输出改为调用 `submit_phonics`。
  2. `submit_phonics` 在 sidecar 内做确定性校验——音节去掉连字符必须拼回单词、IPA 用斜杠包围、拼读规则必须原样取自规则表（新增 `Irregular | 不规则拼读` 兜底）、必填字段非空；不通过则作为工具错误返回问题清单，模型修正后重交，通过才结束本轮。
  3. Rust 只接受本批请求中的单词（忽略大小写、去重）；模型没有返回的单词标记为失败（旧实现会让它们一直停留在“分析中”）。
  4. 两条批量管线（`analyze_extracted_words`、`analyze_text_with_batching`）统一经 `services/phonics_analysis.rs::PhonicsBatchAnalyzer`，回退策略同 D08。
- **未迁移**：单词级 `analyze_phonics_with_model`（JSON 版）仍走旧实现，随 H4 一并评估。

## D12 · 2026-10-07 · 全部 LLM 功能迁移到 agent；无界面入口的旧路径直接删除；迁移完成后移除回退

- **背景**：用户要求“全部迁移到 agent”，并按场景优化提示词。
- **决定**：
  1. 盘点前端实际调用：单词级拼读分析（`analyze_phonics_with_model`，仅被未渲染的 `WordImporter` 组件使用）与 `analyze_text_with_batching` 没有界面入口——**直接删除**（含 `phonics_agent.md`、JSON 拼读解析、`AIService::chat_completion`），不做迁移。

## D13 · 2026-10-07 · 学习计划：模型只做“排序 + 难度 / 优先级判断”，日程由代码确定性计算

- **背景**（需求调研）：旧实现让模型输出整份日程 JSON（日期、每天哪些词、复习第几次），无任何语义校验——会漏词（漏掉的词静默退出计划）、日期越界、同一天同词既新学又复习（该天永远无法“完成”）、长词表输出被截断；提示词的复习规则互相矛盾（7 天表只有 3 次复习但复习次数可选 4–5、“均分”与“前 30% 学 60%”冲突），语气面向成人。
- **决定**：
  1. 模型任务 `plan-word-order`：读入全部单词（id / 单词 / 中文），给出**学习顺序**（由易到难、同主题或同拼读模式相邻）以及每词 `difficulty`（1–5，按小学生视角的拼读难度）与 `priority`（high / medium / low），通过 `submit_learning_order` 交付。
  2. Rust 确定性生成日程（`services/study_planning.rs`）：
     - 学习天数 L = ⌈周期 × 比例⌉（轻松 100% / 标准 80% / 强化 60%），并保证每天新词不超过上限（15 / 30 / 50），必要时把 L 延长到整个周期；
     - 按模型顺序把新词均分到前 L 天（余数给前几天）；
     - 复习按间隔重复 +1、+2、+4、+7、+15 天取前 N 次（N = 复习次数），超出周期的复习丢弃；同词同日不会重复；
     - 元数据（总词数、起止日期、计划类型）全部由代码计算；空白日不生成。
  3. 模型漏掉的词追加到顺序末尾（难度按长度估计、优先级 medium），重复 / 未知 id 忽略——保证每个词恰好新学一次。
  4. 输出仍为原 `StudyPlanAIResult` 结构，预览、保存、详情页、日历、练习均不需改动；规划进度仍写原进度管理器（前端轮询契约不变），取消通过 RPC `abort` 中止 sidecar。

## D14 · 2026-10-07 · 单词例句随拼读分析一并生成；TTS 用固定语音指令稳定朗读风格

- **背景**：用户希望创建单词本时为单词生成例句，练习时既能听单词也能听例句；并反馈“单词朗读每次风格有些不同”。
- **调查**：后端 TTS 缓存有效（键 = 文本 + 音色 + 资源 + 语速 + 采样率，测试库中 `Cat` 命中 5 次，同一文本之后永远是同一段音频）；差异来自豆包 2.0 是生成式模型——同一文本连续合成 3 次结果都不同（实测时长 1.06–1.63s），每个新词第一次合成时语调随机，单个单词尤其容易读成疑问 / 夸张语气。
- **决定**：
  1. 例句在 `phonics-batch` 同一次调用里生成（不另起任务）：`submit_phonics` 增加 `example_sentence` / `example_translation`，工具校验 3–12 词、句首大写句末标点、纯英文、包含该单词（允许复数 / -ing / -ed 等常见变形）、翻译含中文；提示词规定小学课本难度、贴近孩子生活、不套模板。
  2. 存储：迁移 040 给 `words` 加两列（可空）；例句与翻译成对保存，缺一项都不存；再次导入时新结果没有例句则保留原例句。已有单词不回填。
  3. 练习页：第一步显示完整例句（高亮单词）、第二步挖空、第三步只显示中文，作答后显示完整例句；例句可点按朗读，自动朗读只读单词，读完后预取例句音频。
  4. TTS 增加 `style`（word / sentence）：对支持指令的 2.0 资源（seed-tts-2.0 / seed-icl-2.0）通过 `additions.context_texts` 发送固定的“老师示范”指令，风格（带版本号）进入缓存键；1.0 音色不发指令。旧缓存因此对单词失效一次（重新合成后固定）。
- **未定**：指令能多大程度减少差异需要人耳判断；A/B 样本已交给用户试听，不满意可去掉指令或改用 1.0 音色。

## D15 · 2026-10-07 · 每词 5–8 条例句（一对多表），练习页左右两栏

- **背景**：用户要求练习页改为左右两栏、右栏列出例句并可点选朗读，每个单词至少 5 条例句；同时页面要按窗口高度自适应，避免输入框 / 确认按钮被挤出视口。
- **决定**：
  1. 新表 `word_examples`（迁移 041，`ON DELETE CASCADE`，`sort_order` 保序），040 的单列例句迁入后不再读写——不在 `words` 上堆 example_2…example_8 列。
  2. `submit_phonics` 的 `examples` 改为 5–8 条 `{sentence, translation}`，逐条沿用 D14 的校验并拒绝重复句；提示词要求由易到难（第 1 条最简单，用于自动朗读）、场景与句式各不相同。
  3. Rust 侧只保存句子与翻译齐全的例句、去重；重新导入时新结果有例句才整体替换。
  4. 练习页：页面固定为窗口高度，左栏卡片信息区内部滚动、输入区固定在底部；右栏例句列表自身滚动；≤900px 宽改为上下排列并恢复页面滚动。例句显示随步骤变化（完整 / 挖空 / 仅中文，作答后完整）。自动朗读 = 单词 + 第 1 条例句；点击任一例句朗读该句，只预取第 1 条。
- **代价**（15 词评测）：拼读批量分析耗时 49s → 142s、费用 $0.031 → $0.085；校验退回 2 次。可选优化：例句拆成与拼读并行的独立任务，或提高批次并发。

## D16 · 2026-10-07 · 单词讲解：agent 实时生成 Markdown，流式显示，按单词缓存

- **背景**：学生不理解某个单词时，希望在练习页右栏看到像老师一样的深入讲解（结合例句与单词基础知识），可缓存、可刷新。
- **决定**：
  1. 新任务 `word-explain`（`prompts/agent/word_explain.md`，无工具）：输入单词已有资料（释义、词性、音标、音节、拼读规则与讲解、全部例句），输出固定八节的 Markdown（一句话记住 / 怎么读怎么拼 / 意思和用法 / 变一变 / 例句里的它 / 别和它搞混 / 记忆小妙招 / 考考你）。这是展示用的长文本，**例外于 D05“结构化结果只经 submit_* 工具”**：直接取 assistant 文本，Rust 侧只做去包裹代码块与最短长度校验。
  2. 流式：`run_task` 的 `TextDelta` 经 Tauri 事件 `word-explanation-delta {requestId, wordId, delta}` 推给前端，前端按 requestId 丢弃过期增量；完成后以服务端清洗后的全文替换。
  3. 缓存：`word_explanations`（迁移 042，一词一份，`ON DELETE CASCADE`）；打开页签先读缓存，没有才生成；“重新生成”覆盖缓存。换词后旧请求仍会写缓存（下次直接打开）。
  4. 练习页右栏改为「例句 / 单词讲解」页签（两个页签都保持挂载，切换不打断生成）；第二、三步作答前讲解默认遮住（讲解含单词拼写），可手动“仍然查看”，作答后自动显示。
  5. 前端用 `react-markdown` + `remark-gfm` 渲染（不渲染原始 HTML）。
- **实测**（K3 low，cake）：21.0s、978 字、518 段增量。

## D17 · 2026-10-07 · 讲解改用正规记忆方法与正确性自查；例句可由 AI 补充 / 重新生成

- **背景**：用户质疑讲解里的“记忆小妙招”（如把 all 说成 ball 拿掉 b、“大家都能玩所以是全部”）不符合英语母语者的学习习惯，要求审视专业性与正确性；并希望例句页签也能让 AI 补充或重新生成，交互与讲解一致。
- **基线评测**（`agent/eval/eval-explain.mjs`，8 类单词）：发现字母赋义（“c 像盘子、k 是刀”“i 是蜡烛、gh 是幽灵”）、错误构词（teacher = tea + cher“喝茶的人”）、谐音（elephant）、读音说法不准（said “ai 读短音”）。
- **决定**：
  1. `word_explain.md` 改为以成熟方法为骨架：音—字母对应（orthographic mapping）、词族 / 押韵（onset-rime）、构词（morphology）、音节分块、心形词（Heart Words，只用于真正不规则的部分）、看-说-盖-写-查（Look-Say-Cover-Write-Check）、边拼边说、画面 + 句子；明确禁止中文谐音、编造词源、无关词语义硬联系、给字母赋予含义。
  2. 增加“输出前逐条自查”：词族成员必须同拼同音（eight ∉ -ight）、心形部分不含 igh/ai/ph 等规律组合、同音词必须完全同音、对其他词读音的断言必须准确、构词必须真实。

## D26 · 2026-10-07 · 短文：不限制词数，内容质量优先

- **背景**：用户指出“合计最多 15 个词”没有道理；按“每 N 个词放一个目标词”的密度规则会让短文模式化，成为“按规则对齐的语法句子”，失去阅读价值。实测（16 个必用词，A1）也印证：模型写成按行程逐词打卡的流水账，并出现为用词而硬凑的句子。
- **决定**：
  1. 不设目标词上限（至少 1 个）；篇幅只作为长度与丰富程度的参考，为自然用上所有必用词可以适当写长；工具只拦明显没写完整的短文（< 参考下限的 60%），不再按词数区间退回重写；AI 挑词“最多 N 个、宁缺毋滥”。
  2. 提示词改为“先当作家再当老师”：围绕一个核心事件展开、不写流水账、具体细节与对话、句式多样、目标词为内容服务，交稿前自查“去掉目标词故事还值得读吗”。
  3. `submit_passage` 增加必填的 `outline`（goal / problem / turn / ending），先构思再写；写短文任务思考档改为 medium。
- **实测**（Kimi K3，A1）：5 个必用词 + 挑 3 个 → 有起因、连续小麻烦、解决与幽默收尾的故事（99 词，35s）；16 个必用词 → 后半段有完整情节（130 词，52s），前半段受词表本身（整套出行流程）影响仍偏行程顺序。代价：生成时间约增加 10–25 秒。

  1. 新 agent 任务 passage-plan（`passage_plan.md`，工具 `submit_passage_plan`，medium 思考档）：决定写 1–4 篇，每篇给英文标题、中文构思（主角与目标 / 麻烦或意外 / 发展与解决 / 结尾）、所用的词、建议篇幅，并用 `note` 说明为什么这样规划；只在词能自然放进同一个好故事时写一篇，词分属不同场景或一篇装不下时拆分。用户可写调整意见重新规划。
  2. Rust `plan_from_submission` 校验：词只来自必用词与候选池（AI 挑选合计 ≤ ai_pick）、每词只归一篇、漏掉的必用词补进词最少的一篇、无词或无构思的篇目丢弃。规划不入库。
  3. 生成时 `GeneratePassageRequest.plan_item` 带上用户确认（可改标题、构思、篇幅、取消某篇）的那一篇，写作消息加入“按已确认的构思来写”，词以数据库为准（有 id 的词必须存在）。前端逐篇顺序生成，显示每篇状态，失败可单独重试。
- **实测**（Kimi K3）：16 个出行词 → 拆成“机场 + 海关”“酒店 + 城市”两篇，各有核心事件（31s）；5 个词 → 一篇完整故事，未挑无关候选词（15s）；按构思写的短文严格遵循人物、事件与结尾并补充了细节（45s）。

  4. **字幕纠偏** `videos.subtitle_offset_ms`：不改原始时间，`VideoRow::cues()` 是唯一换算点，显示 / 规划 / 切分都用它；按需翻译的中文写回原始字幕（下标对齐）。
  5. 计划里不带题组的切片任务即「看视频跟读」（不扩 mode 的 CHECK），听力题组用原声。
- **原因**：关系建在已有的短文体系上，练习 / 出题 / 计划全部复用；索引让关联查询的耗时只与命中数有关，长期使用不会变慢；标签通用、可管理，避免 AI 生成的标签无限增长后无法整理。

## D38 · 2026-10-09 · 练习以完整的句子为单位：AI 断句，规则兜底

- **背景**：字幕按屏幕宽度断行，一句话常被拆成几条；切成短文后朗读、听句拼句、跟读都是半句半句的。字幕来源质量参差，标点可能缺失或不规范，只靠标点合并不可靠。
- **决定**：
  1. 导入视频时的字幕处理改为「整理字幕」agent 任务（`subtitle_prepare`）：AI 按意思判断每条是否接着上一条（`Cue::join`），同时给缺中文的条目翻译；每块 40 条、附上前一条作上下文，3 块并行，逐块写回。字幕已有中文也要做断句。
  2. `services/sentences.rs::group_cues` 是断句的唯一 owner：AI 判断过的按它（只用宽的硬上限防异常长句），没整理过的按标点、停顿、换人说话推断（软上限约 28 词 / 12 秒）。
  3. 切分时短文句子按断句合并（`clip_sentences`）；AI 规划的片段边界对齐到整句（`align_to_sentences`，最多补 3 条，相邻两段在同一句中间分开时这句归前一段）；按字幕自动切分也不在半句中间切；编辑器字幕列表把同一句排成一块。
  4. 已切出的片段不改（题组与练习记录基于现有句子），重新切分即按新规则。
- **原因**：断句是理解问题，交给 AI；上限与对齐是确定性约束，放在代码里，AI 结果异常时也不会产生超长句或跨段的半句。

## D39 · 2026-10-09 · 一个视频多个切分规划；切片与短文在界面上分开

- **背景**：同一个原始视频可以从不同角度切（按场景、按语法点、按难度……），原来一个视频只有一份规划草稿。短文库里混着视频切片，素材边界不清。
- **决定**：
  1. `video_plans` 表（迁移 061）：每个视频多个规划（名字 + 草稿），原草稿迁成「规划 1」；AI 规划与切分都按 planId；`video_clips.plan_id` 记来源，删除规划时置空、片段保留；两个规划里起止相同的片段只切一次。「AI 规划」的要求建议属于视频（`videos.plan_suggestions`）。
  2. 编辑器顶栏按流程收拢：① 字幕（整理字幕，角标显示进度 / 剩余）② 规划（切换、新建、复制、改名、删除，AI 规划、按字幕自动切分、查看片段）③ 开始切分。
  3. 切片仍借用短文的练习 / 出题 / 作答结构（内部实现），但界面上只在视频库出现：短文库列表、统计与标签计数都不含切片；短文与切片在学习计划里按学习场景组合。
- **原因**：规划是「看一个视频的角度」，天然可以有多个；切片作为独立的素材类别管理更清晰，组合是计划的职责；存储复用避免为切片再做一套练习体系。

## D40 · 2026-10-09 · 字幕整理是内部步骤，不做成用户操作

- **背景**：编辑器里曾有「字幕 ▾ / 整理字幕（N 条）」与片段面板的「翻译这一段」。用户不知道这是什么、何时该点，还要靠说明文字解释。
- **决定**：删掉这些入口与命令（start_video_translate）。整理字幕只在需要它的流程里自动完成：导入时整部、AI 规划与切分开始前补还没整理的（同一任务内，阶段「AI 正在读字幕」）；失败记 WARN 继续，按标点推断断句、切分时补中文兜底。
- **原因**：数据准备不是用户的目标；暴露成按钮只会增加理解成本。

## D41 · 2026-10-09 · AI 生成素材时自动打标签；标签成为侧边栏入口

- **背景**：标签只在 AI 切视频时自动打上，单词本、短文要用户手动加，跨素材按主题归类缺数据；标签也只能在各素材库里当筛选用。
- **决定**：
  1. 提词、按描述生成单词、写短文、导入材料翻译的提交工具加可选 `tags`（1–3 个中文标签，写通用的场景或话题）；用户消息附上全部已有标签（按使用量排序，最多 200 个，视频规划同样），要求先从已有的选：意思相同、相近或只是范围大小不同（「旅行」/「出国旅行」）都用已有名称，新起的不能是同义、近义或加修饰的变体，避免同义标签越来越多。Rust 侧统一清理（`tags_from_submission`）。
  2. 只加不删：AI 标签加到素材已有标签上；单词本在单词保存成功后加，短文与入库同事务。
  3. 侧边栏「标签」分组按素材数列出有内容的标签，进入标签页按种类（片段 / 短文 / 单词本 / 原始视频）分页签，复用各素材库列表的嵌入模式（固定标签）。
- **原因**：标签是跨素材组合学习内容的纽带，应当在生成时就有；标签页复用现有列表，交互与各素材库一致，不另做一套。

## D42 · 2026-10-09 · 短文目标词的单词卡不依赖单词本

- **背景**：短文的目标词里有不在单词本的词（AI 选的、导入时识别的、阅读时自己加的）。只有收进单词本才有音标、拼读、例句、讲解，学短文时被迫先建单词本。
- **决定**：
  1. `word_cards`（063）：按小写单词存一份学习资料（音标、词性、释义、音节与拼读、例句），各短文共用；用批量拼读分析（与单词本加词同一个 AI 任务）生成，后台任务 `word_cards`，短文的「目标词」页签发现缺卡时自动补。
  2. 讲解与答疑支持单词卡（`card_word`，前端用负数 id 代表），与单词本的词体验一致；收进单词本后以单词本里的为准。
  3. 读原文时可以选中一个词加成目标词（指定单词）：必须在正文里出现（含变形）、不重复；单词本里有的直接关联。
- **原因**：短文本身就是学习材料，单词的学习资料不应以「先收进单词本」为前提；单词本只在需要练习、进计划时才用。

## D43 · 2026-10-10 · AI 是贯穿学习过程的陪伴老师，不是内容生成器

- **背景**：单词卡上的「AI 讲解」是一块「生成 / 重新生成」的固定内容，下面再挂一个提问框，用户会把它当成一次性生成的说明文字。
- **决定**：
  1. 「AI 讲解」改为「AI 老师」：一段围绕这个词的对话。打开即由老师先开口讲（原讲解任务），学生接着问（原答疑任务），同一个对话流；没有生成 / 重新生成按钮，换个讲法就是一句追问。会停下来看的环节自动开口，否则老师问一句「需要我讲讲这个词吗？」。
  2. 同一个词的对话在单词卡、练习右栏、短文与视频里共用（本次打开应用期间按词保留）。
  3. 后续：老师知道学生所在的场景（短文的哪一句、视频的哪段台词、练习的哪一步、刚答错了什么），开场与回答结合场景；在练习、阅读、听力等环节提供就地的老师入口。
- **原因**：AI 在拼读里既负责规划与生成，也是学习中的陪伴者；对话式比固定内容更符合「老师」的角色，也更好地承接追问。

## D44 · 2026-10-10 · 听力也考选词填空（听句填空）

- **背景**：题组里的选词填空在听力模式被直接隐藏（D 早期决定：听力不看原文、不考选词填空），用户以为没有生成。
- **决定**：听力里选词填空改为「听句填空」：只显示含空位的句子并挖空，点句首听这一句，从词库选词；与其它题一样必须作答、计入判分。交卷后原文里同样标出填空结果。
- **原因**：填空的词正是目标词，听句辨词是标准的听力题型；只露出单句不影响「不看全文」的听力练习。

## D45 · 2026-10-10 · 学习内容的颗粒度：词汇本（单词 + 词组）与句子分析（句式、语法、功能）

- **背景**：只支持单词；但很多词组不能拆成单词理解，句式、语法、交际功能是读短文、看视频时更重要的学习层次。
- **决定**：
  1. 「单词本」改为「词汇本」，条目分单词与词组（短语动词、固定搭配、习语、固定短语）；都能当目标词、有单词卡、进学习计划。
  2. 句式、语法点、交际功能不进词汇本，作为短文与视频的「句子分析」长在具体句子上；句子里的词组可一键收进词汇本。
  3. 拼读规律、构词作为浏览与关联维度（知识点），不是要背的条目。
  4. AI 老师掌握这些层次与基本教学技能（`fragments/teacher/knowledge.md`，答疑、讲解、开放题评分共用）。
- **顺序**：AI 老师教学知识（已做）→ 词汇本与词组 → 句子分析 → 功能表达与视频结合 / 拼读与构词浏览。

## D46 · 2026-10-10 · 句子分析：长在句子上，按句子缓存，可就地问老师

- **背景**：D45 定下句式、语法、交际功能不进词汇本，而是作为短文与视频的「句子分析」。
- **决定**：
  1. 短文原文与视频片段台词的每一句都可以打开「句子分析」：句式公式、成分划分、语法点、交际功能（含同功能的其他说法）、词组、发音要点。由 agent 任务 `sentence_analyze` 生成，`submit_sentence_analysis` 交付；Rust 按原句校正（片段必须出自原句、成分有序、词组原形合法），不靠模型自觉。
  2. 按句子文字缓存（`sentence_analyses`，065），各短文共用；用户点「重新分析」才覆盖。按需生成，不预先批量分析整篇（成本与等待都花在学习者真正想看的句子上）。
  3. 句子里的词组一键加成这篇的目标词，之后沿用目标词 → 单词卡 → 加入词汇本的路径（收进词汇本时有单词卡就沿用，不重复做拼读分析）。
  4. 分析面板里可以就地「问老师」：AI 老师的对话以这句话为主题（原句、译文、前后句、已有的分析），与单词的对话分开保存。
- **原因**：句式与功能离开具体句子就失去语境；缓存避免同一句重复花钱；问老师承接分析看不懂的地方。


## D47 · 2026-10-10 · 词形与词组识别不再靠手写规则：词形库 + AI 标注

- **背景**：判断「原文是否用到某个词 / 词组」靠手写的词尾规则、不规则动词表、小品词表、占位词表，前端、sidecar、Rust 各写一份，既列不全，三端又会不一致（曾导致写短文时 sidecar 放行、Rust 拒绝，整篇失败）。
- **决定**：
  1. **词形库**（B1）：单词变形用 WordNet 3.0 的词表与官方不规则变形表 + morphy 算法还原，数据 `shared/lemma/wordnet.json`（`scripts/lemma/build.mjs` 从官方包生成，校验 sha256），TS 实现 `shared/lemma/morphy.ts`（前端与 sidecar 共用），Rust `src-tauri/src/lemma.rs` 同一算法同一数据，两端用 `shared/lemma/cases.json` 核对。一个词本身已是某词性的基本词时不再对该词性去词尾（bed 不还原成 be）；词典外的词只按 WordNet 的去词尾规则比较。手写的变形规则与不规则动词表全部删除。
  2. **AI 标注**（B2）：词组在原文里的写法（gave up、picked it up）由 AI 在写短文、导入材料、视频切分时标注，读原文时划选加入的按选中的原文记录；高亮、挖空、填空按标注定位，程序只核对写法确实在原文里。小品词 / 占位词规则随之删除。
  3. **跨素材查找**（B3）：词索引按原形存，查找不再逐个猜变形。
- **原因**：语言事实（词形变化）用权威数据，语境判断（这句里的词组是哪几个词）交给读过全文的 AI；代码只做核对。

## D48 · 2026-10-10 · 素材创建流程连贯：场景一路带下去，AI 建议可多选追加，耗时规划是后台任务

- **背景**：新建词汇本时写的场景描述，到「AI 生成」时用不上，建议是写死的示例；新建短文的场景与词汇本无关，内容规划在页面里同步等待，离开就丢；AI 建议只能单选、换一批会把已选的冲掉。
- **决定**：
  1. **场景一路带下去**：新建词汇本后直接进入 AI 生成；有场景描述时词汇需求可以不填。词汇需求建议由 AI 按场景给（`suggest_vocab_topics`，`vocab_topic_suggest.md`）；新建短文的场景默认带入所选词汇本的场景描述，场景建议由 AI 按词汇本与要用的单词给（`suggest_passage_scenes`）。不再有写死的示例建议。
  2. **建议可多选、换一批追加**：前端 `SuggestionChips` 统一交互——选中的建议拼进输入框，换一批保留已选、追加不重复的新建议（`exclude` 传给 AI）；词汇需求、视频切分要求、短文场景、规划调整建议都用它。
  3. **内容规划是后台任务**：`start_passage_planning`（kind `passage_plan`，detached，可取消），结果在 job.result；新建短文页记住草稿，离开再回来能接着做。规划的调整建议由 AI 针对这份规划给出（`adjustments`）。
  4. **过程可见、终点明确**：词汇本详情在 AI 分析时就地显示逐词进度，不显示空状态；新建短文全部生成完后显示结果卡片（成功 / 失败篇数、逐篇打开或重试）。
  5. AI 标签只给新建的（原本没有单词的）词汇本打，往已有词汇本加词不追加。
- **原因**：用户写过的信息应该在后续每一步被用上；AI 建议是给用户挑选的素材，不应该互相覆盖；超过几秒的 AI 工作都走后台任务，与其他素材一致。

## D49 · 2026-10-10 · 朗读：固定只读英语，风格是可选预设，参数计入缓存

- **背景**：豆包 2.0 音色会把句子里的数字读成中文；中文语音指令下各句风格不稳定；语速以外的参数不可调。
- **决定**：
  1. 单词与句子朗读都传 `additions.explicit_language = "en"`；语音指令（`context_texts`）改为英文，并要求各句语气一致。指令只对 2.0 资源（`seed-tts-2.0` / `seed-icl-2.0`）发送。
  2. 句子朗读风格是预设：老师示范（默认）/ 自然口语 / 讲故事 / 新闻播报 / 自定义（≤200 字，建议英文）；单词发音始终是平稳的示范语气，不受风格影响。另可调音调（`post_process.pitch`，−12～12）与音量（`loudness_rate`，−50～100）。偏好存 `app_settings` 的 `tts.preferences`（`services/tts.rs` 归一化）。
  3. 指令内容（哈希）、语种、音调、音量都计入缓存键，换设置后重新合成，不会播出旧风格的缓存。
  4. 音色预设为 15 个官方英文 2.0 音色（标口音、性别、适用场景）；仍可填其他音色 ID。
  5. 设置页试听与实际朗读同一方式：逐句合成、连续播放（实际朗读是一句一请求，整段合成的试听会比实际更连贯，误导选择）。
- **原因**：朗读是学习材料，语言必须确定；风格因人而异，给预设而不是让用户写指令；缓存键必须覆盖所有影响声音的参数。

## D50 · 2026-10-11 · 短文挑目标词：挑值得学的词，挑够，拆篇均衡

- **背景**：新闻词汇本（72 词）+ 默认学习者档案（小学生 A1）+ 挑词偏好「难度适中、常用」时，内容规划挑出 said、get、more、days、called 这类最基础的词，拆成两篇时一篇只分到 plan、more 两个词。真实调用复现：模型把「高频」「贴合 A1 水平」理解成挑最简单的词；提示词只在「按描述生成、不给单词」时说过不选基础功能词；「挑不满就少挑」让模型倾向少挑。
- **决定**：
  1. `passage_plan.md` / `passage_generate.md`：目标词是要学的词——只挑学习者还没掌握、学了用得上的实词或词组；人人都会的基础词和专有名词不选（故事里照样可以用）。合适的词足够时挑满 N 个，真不够才少挑。
  2. 挑词偏好改写（`passage_rules::pick_preferences`）：适中 =「略高于这位学习者现有水平」，常用 =「日常生活和常见文章里用得多的实用词」，不再说「高频」。

- **证据**：`agent::tasks::tests::real_passage_plan_picks_worthwhile_words_with_kimi_k3`（同一词表与场景）。改前两次：called, plan, hopes, said, more, instead, get, days, measure, ahead / according, called, days, get, hopes, instead, measure, more, plan, said；改后两次：according, ahead, cap, challenging, hopes, instead, measure, plan, policy, voluntary / 两篇各 5 个（plan, policy, hopes, measure, according · challenging, instead, accept, ahead, response）。

## D52 · 2026-10-11 · 非文本素材交给 pi 自主处理：skills 指导 + 只读文件工具 + 程序核对

- **背景**：学校发的单词海报、双语对照讲义等排版素材，文字层是乱的（分栏交错、注释夹在句中、音标拆行），我们自己的文字提取整理不出来；为每种格式写解析与清洗规则既列不全，也让代码越来越复杂。
- **决定**：
  1. 文本型文件（txt / md / srt / vtt）仍由我们的算法预处理；PDF、图片、Word 等交给 pi 的「素材阅读」任务（`material_read`）。

  4. 模型能否看图由模型自身能力决定（pi 目录 / 同步信息，`ai_models.supports_images`），不让用户配置；不能看图时看图工具提示改用文字工具，由 pi 自己退化。

- **原因**：版面理解是 AI 擅长、规则写不完的部分；确定性的事（读文件、核对原文）留在代码里。实测（样例 BBC 双语讲义 8 页）：Kimi K3 与 DeepSeek V4.1 Flash 看图均整理出 30 句 / 29 句译文 / 21 词组 / 26 词汇；强制不能看图时 pi 只读文字层得到同样结果。

## D63 · 2026-10-15 · 字幕断句：识别按逐词时间组句，长句只断在安全的地方

- **背景**：学习者反馈识别出的字幕常把一句话卡断（如断在 that 后面），原声没问题。实测 small.en 默认输出全小写、无标点，whisper 按停顿与长度分条，一条里混着两三句的边界；整理字幕的 AI 只能判断相邻两条合不合并，不能在一条中间断开，怎么整理都断不对。另外提示词要求 AI 把长句拆开（它只能选字幕条之间的位置，常落在虚词后），`sentences::group_cues` 的长度上限在当前位置硬切（Apollo 11 字幕里切出「the burdens and ‖」「two elevators for ‖」）。
- **决定**：
  1. 识别：whisper 加开头提示（一句带标点和大小写的英文，`--prompt`），输出逐词时间（`-ojf`）；按词重新组句，一句一条字幕，时间来自词（`subtitle_recognition::cues_from_whisper_json`）。开头提示在静音处被原样写出的段去掉；音效标注、`>>` 换人说话照旧处理。逐词结果读不了时退回 whisper 的分段（srt）。DTW 词时间在当前构建不生效，不用；播放时还有本机发音模型逐句对齐兜底。
  2. 断句规则一个 owner（`services/sentences.rs::group_spans`），字幕条与识别出的词共用：停在 that / to / the 这类词上（后面一定还有话）且停顿不超过 0.8 秒时一定接着下一条，AI 判了不合并也一样；一句超过 35 词或 15 秒时找安全的地方断开（句末、逗号分号后、but / because / which 这类词前，and / or 要有停顿，或明显停顿处），两边尽量匀；找不到就保留长句，超过 50 词或 25 秒才断在停顿最长处（尽量不在虚词后）。AI 判断连成一句的，只按 50 词或 25 秒的上限拆（新闻、访谈里 35 词以上的整句很常见，按 35 词拆出来是半句话）。切分时整理还没做完，先等它做完再切，句子要用 AI 的断句。前端 `video-editor/plan.ts::continuesSentence` 同步虚词规则。
  3. 提示词 `subtitle_prepare.md`：AI 只判断是不是同一句话，不再负责拆长句；明确停在虚词上时一定是同一句。
- **影响**：已识别的视频要「重新识别」才用上新的分条；导入的字幕文件仍按条整理（时间只有整条，不在条内重新切分）。真实数据对比见 `.claude/work/subtitle-segmentation/evidence.md`。

## D65 · 2026-10-16 · 场景片段四个练习模式；AI 内容讲解；影子跟读整段评估；精听只填关键词

- **背景**：场景片段原来分「观看 / 跟读 / 听力」三个页签：没有帮学习者弄懂内容的讲解；「跟读」只有听后复述；「听力」只有拼单词卡，练不到听清每个词。中间试过做成「盲听 → 理解 → 精听 → 跟说 → 回听」的步骤条（带自评、标没听懂、整句听写逐级降难度、同步跟读与叠放对比），用户试用后认为步骤式太繁琐、自动播放吓人、不少环节练不出效果，改回页签。
- **决定**：
  1. 四个页签：理解 / 盲听 / 跟读 / 精听（试过加「回听」——不看字幕再看一遍，和盲听一样、没什么用，去掉）。切换时停下正在播放、正在跟读的，**不自动播放**；进度只在这次打开期间保留，素材不记练习（学习计划里的记录以后再定）。
  2. 理解 = 视频占满宽度（没有台词列表，台词、点词、句子分析在跟读页签）+ **AI 内容精讲**（新 agent 任务 `clip_guide.md`，无工具、Markdown 流式，`clip-guide-delta` 事件）：学生先要真正听懂内容才建立得起听力，所以以讲清内容为主线，像老师拆书一样先讲全貌、再逐段精讲，背景、句式（公式 + 新例子）、词汇与听力难点穿插在讲到的地方，不各自列成脱离内容的清单，最后回顾。一个片段一份存在 `passage_guides`（071），打开片段时还没有就生成，可重新生成；用「讲解」的任务模型。
  3. 盲听：不显示字幕，没有台词列表；可以「遮住画面」只听声音（不少视频画面里本身印着台词），默认遮住，记在本机。布局不变（页签在视频下面，跟读、精听时右边 380 宽的练习栏），视频宽度不变、高度最多约半屏多（56vh，画面等比缩放两边留黑），下面的内容第一眼看得到。
  3a. 视频下面用标准的视频控制条（`clip/PlayerBar.tsx`，深色，挨着画面）：按句分段的进度条，播放 / 暂停、上一句、重听这句、下一句、时间，速度、字幕、每句后暂停（理解）、遮住画面（盲听、精听）、音量、全屏（只在理解、盲听：跟读、精听全屏会盖住右边的练习卡片；窗口进入系统全屏，退出时恢复成原来的样子，权限 `core:window:allow-set-fullscreen`）；快捷键 空格 / ← → / R / M / F / Esc，在输入框里不响应。
  4. 跟读两种：逐句跟读——一次只练一句的卡片（大字、译文、原声 / 慢速、「跟读」= 播原声 → 开麦 → 评分，结果在下面，进度条按每句结果着色、点哪段练哪句，「读完自动下一句」默认关，句子分析也在卡片上）；原来在长台词列表里一路自动往下、每句一堆小按钮，不好控制也看不清结果。影子跟读——和逐句跟读同一个结构的卡片，从第一句起固定分成约 30 秒一段（一整段练完才看得到结果、中途停下白录），只显示这一段的台词，原声逐词标出读到哪里，要戴耳机。两种跟读共用一个卡片外壳 `clip/PracticeCard.tsx`：顶部固定进度与状态，中间只滚台词与结果，底部固定控制条（‹ 上一句（段）· 原声 · 慢速 · 译文 · 练习设置 · 跟读 · 下一句（段）›，除了「跟读」都是带悬停说明的图标；只管右边卡片的译文、设置都在这里，不放在视频下面）；「读完自动下一句」在练习设置里。跟读卡片里的台词直接用原文页签的 PassageReader（`clip/ClipSentences.tsx`），当前句放大、逐词高亮、聚焦模糊、词汇标记与单词卡片和原文一致；原声在放时按台词逐词对齐的时间逐词高亮，影子跟读可聚焦当前句，两项都在练习设置里、默认开。原文页签用原声朗读片段时也接上了逐词时间（`ClipSource.words`）。PassageReader 读到的词不再用负边距 + 1.15 倍放大（会盖住两边的空格），改为 1.06 倍 + 不占位的外圈描边。精听用同一个外壳（`CardShell`）：底部固定 ‹ · 播放 · 慢速 · 提示 · 看答案 · 设置（挖空少 / 多）· 核对 / 下一句 · ›，主操作保留文字，其余是图标。跟读卡片只有一个按钮管跟读（练的时候是「停止」：录音时点它就是读完了，放原声时点它就是不练了；评分时变灰）。原来的长台词列表、点词卡片、译文显示方式与聚焦设置去掉（原文页签里都有）；放完交给本机评估 `assess_shadowing`：把台词对到录音上，逐句给出说的位置与每个词说没说出来。不逐音打分——整段逐句完整评分实测 23 句 49 秒（正式版），太慢。「说出来了」= 对齐时这个词的音与每帧最像的音的平均对数概率差 ≥ -4（`SAID_FIT`），且那段录音里有说话的音量。校准：原声延后 600ms 当作跟读，全部句子判为说了（少数原声里本就含糊的词除外），三处换成底噪的部分判为没说，落后时间都量出约 600ms。
  5. 精听：学习者打不了长句、整句听写费时间正确率又低，改为逐句只填挖掉的词（`utils/dictation.ts::pickBlanks`）：「挖得少」只挖 1–3 个关键词（词汇优先，其次长的实词），「挖得多」约四成的词、也挖读得轻的虚词（听力真正的难点）；不挖数字、人名。画面默认遮住（常印着台词）。填错标红可再改，「提示」逐个露出字母，可看答案，填错的词可加入词汇；进度条按一次填对 / 改了才对 / 看了答案着色；换句都接着播这一句；做完列出结果，可只重练没一次填对的。
  6. 台词对齐改为逐词（`align_words`），超过 3 分钟的声音按句子分段对齐（约一分钟一段，前后各多带一句作上下文、结果不用）；实测与整段对齐相差不到 50ms、更快。片段对齐上限从 5 分钟提到 30 分钟。
  7. 「整段不切分」只用于 5 分钟以内的视频：场景片段要逐句精听、跟读，太长一次练不完。
  7a. 讲解的正确性（回归测试发现两句台词的片段被写出「gift 的 g 不发音」并配 /ɡɪft/、把 give sth to sb 叫双宾语、推测父亲已不在）：提示词加「篇幅跟着台词走」「只讲台词和标题里有的，不猜人物关系与情节」、发音与术语底线和输出前逐条自查；单词讲解的自查要求逐个核对同规律例词的音标。
  8. 原文页签工具栏、视频「内容讲解」标题栏各有一个 AI 老师（学士帽）开关，唤出和单词一样的右侧对话面板，围绕整篇短文 / 场景片段聊（`WordTutorRequest.passageId`：带标题、逐句原文与译文（超过约 1.2 万字截断）、词汇、片段已有的内容讲解；对话按 `passageChatId` 在本次打开期间保留）；和句子分析占同一个位置，开一个关另一个。
- **影响**：原「听句拼句」去掉；README 的场景片段介绍发版前要改；MCP 工具还没有片段讲解。
